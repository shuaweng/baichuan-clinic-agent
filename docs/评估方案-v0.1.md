# Jev Query/Answer 评估方案 v0.1

日期：2026-09-21。状态：可审阅草案；未调用 Jev，未生成当前 Answer，未做人工金标准标注。本项目不是百小医官方系统。

## 1. 评估单位与前五轮

一条记录对应一个当前用户 Query；拿到当前 Answer 后，评估对象是当前 Query–Answer 对，唯一键为 conversation_id + current.turn_id。历史回答不是这次的评分对象。用户所说的 query 维度，在本方案中包含两个层次：Query 层评意图和范围，QA 层评回应是否合格。

默认附带当前 Query **之前最多五个完整 QA 轮次**，按时间顺序排列，不包含当前 QA、不补齐不存在的前文、不提供未来回复。一个轮次是一个用户消息与其对应助手回复；真实系统中的连续用户气泡和工具消息需要先按实际 turn 归组，不能机械按每两条消息切分。

前五轮是 v0.1 的可调窗口，不是 Jev 限制，也不是已验证的最佳长度。只做当轮反馈质检时可保留五轮，不先用模型总结替代原文，以免丢掉否定和对象纠正。长文本按 token 预算处理。窗口之外如果有关键对象、授权、待办或用户纠正，另以 relevant_memory 提供带来源、时间的已知事实；没有查到时明确缺失，不能杜撰“记忆”。后续用同一组样本比较 0/2/5 轮的收益、成本和误报。

用户新一轮的“不对”可以证明用户不满、帮助后续复核旧答案，但不能作为当时在线评估的未来信息。离线回溯须另标评估模式。

## 2. 传入内容与禁止传入内容

**核心输入是产品服务范围、产品能力范围、当前 QA、必要历史，以及判定问题/标准。** 两个范围此前统一收在 product_profile 里：scope_policy 描述服务范围及限制，capabilities 和具体能力清单描述能力范围。它们一直是输入的一部分。

下表不是“每次全部必填”。attachments 仅在诉求依赖附件时补充；execution 仅在需要核验动作结果时补充。已有需求池用于后续判断是否重复已有需求，第一阶段可不提供，只识别候选机会。配置中的 backlog/not_available 是缺失声明，不是可用的需求池。

用于对齐概念的最小完整请求：../data/examples/alignment-minimal-qa.request.json。其中能力支持/不支持为**讲解假设**，当前 Answer 也是临时 mock；不改动原有 100 条待生成 Answer 的样本，也不代表百小医真实能力。此示例把范围显式命名为 service_scope，实际原配置仍使用 scope_policy；这两者都是项目自定义 state 字段，不是 Jev 固定参数。三个问题为便于对齐而精简，尚未调用模型。

| 输入块 | 内容 | 约束 |
|---|---|---|
| product_profile | 版本、服务范围、能力证据、边界、已知能力前提 | 不能把公开宽泛宣传当成原子功能验证 |
| history | 最近至多五轮 QA，包含 turn_id | 历史助手说法不是权威事实 |
| current | 当前 query，QA 模式才含当前 answer | 没有 Answer 不评回复质量 |
| relevant_memory | 更早的相关已知事实及来源 | 不传隐藏场景设定 |
| time_context | 消息实际时间和时区（若有） | 本批未分配，不把生成日期当作对话日期；不能擅自将“明天”解析成具体日期 |
| attachments | 可读文本或不可用状态 | 未读取图片时不得假装看过图片 |
| execution | 已采集工具结果、任务状态 | 未采集不等于没有执行或执行失败 |
| known_requirements | 已有需求池（如实际拥有） | 没有内部需求池时“是否新需求”不评 |

采样分组、故障注入指令、预设期望、人工金标准、生成角色的私有背景均不传给 Jev。prepare_jev.py 使用白名单组装 state。仅按“删掉标签字段”不足以防止未来 metadata 泄漏。

Query-only 模式不传当前 Answer 和当前执行结果，减少回答反过来影响用户意图分类。QA 模式可以一次发送全部 query + QA 问题；若要比较同一 Query 的多种 Answer，建议固定先前 Query-only 结果，避免把输入变化误认为用户意图变化。

## 3. 服务范围与能力范围是两条轴

产品范围草案依据公开官网及授权协议：就医前后信息支持、健康知识与医嘱理解、健康记录提醒、家庭健康管理。详细配置见 ../config/product-profile.v0.1.json。

| 判断 | 含义 | 例子 |
|---|---|---|
| 服务范围内 | 符合产品健康任务定位 | 请求整理复诊清单 |
| 外围/未明确 | 和健康有关，但是否提供该类服务不明确 | 核算保险报销金额 |
| 服务范围外 | 与健康服务无关 | 写普通工作周报 |
| 明示边界受限 | 本项目规则明确不提供或不应承诺 | 伪造病假条、未经授权查他人记录 |
| 能力具体支持已验证 | 已确认具体功能及使用前提 | 未来通过实测或可靠产品文档加入 |
| 仅公开方向支持 | 官网提到该能力，但条件/渠道未实测 | 复诊提醒 |
| 具体缺口已验证 | 明确证据证实具体功能缺失 | 只有后续验证后才能写入 |
| 能力未知 | 没有证据，不等于缺失 | 未确认后自动通知家属 |

公开支持可以作为“值得检查”的预期方向；不能据此指控所有未完成操作都是产品故障。初版 verified_atomic_capabilities 和 explicitly_unsupported_atomic_capabilities 均为空，忠实反映调查状态。服务边界中的限制是研究项目提出的判定政策，**不是百小医内部政策原文**。

## 4. 何为好回答、badcase、需求机会

本项目评价任务回应质量，不声称验证医学结论正确。好回答没有唯一文风，也不必长、礼貌模板多或给出完整结论。

好表现包括：信息充分时覆盖明确诉求；信息缺失时有针对性追问；正确承接人物、时间和用户纠正；尊重明确格式与授权约束；动作成功才声称成功；遇到边界清楚解释并提供可行帮助；用户结束或暂缓时不强行继续。

| 候选问题 | 需要的证据 | 不应误判为问题的情况 |
|---|---|---|
| 漏答/答非所问 | 当前明确诉求与当前 Answer 对照 | 为完成任务而必要的追问 |
| 上下文使用错误 | 用户已说清的对象、约束或纠正被违反 | 前文没提供导致的合理澄清 |
| 明确执行不一致 | 当前声称成功，但日志失败或对象/参数不符 | 没有日志时只能判无法验证 |
| 明示边界违反 | 回答与配置中的明确限制冲突 | 对边界请求作恰当拒绝 |
| 明确交互要求违反 | 用户要求易懂/逐步/特定格式而明显未遵循 | 仅不符合评估者个人文风偏好 |
| 医疗风险信号 | 需要专业复核的诉求或文字 | 不以 Jev 单次判断确定医学对错 |

“失败”是本轮任务结果；“badcase”是依据标准确认值得纠正的表现；“能力缺口”是产品覆盖问题；“新需求”还需要对照既有能力、需求池和人工价值判断。这些可以重叠，不能合成一个万能标签。

能力缺口即使回复得很好也可能存在；回答不好也可能只是已有功能的缺陷。明确范围外、边界受限、不知道产品是否支持的请求，不直接进入“确定新需求”。

## 5. Jev 输出与后续处理

问题配置见 ../config/jev-questions.v0.1.json。

- Query 层：主任务、多个并存意图、服务范围、能力证据、上下文充分性、明确不满、专业复核信号。
- QA 层：诉求覆盖、上下文一致性、执行声称依据、边界遵循、明确表达要求遵循。
- 多诉求用独立 Noul 探针并存，主任务 Choice 允许 mixed/unclear/other；不可把主分类当作穷尽需求。
- Choice 的 confidence 是分布集中程度，不是本项目实测正确率；Noul 无单独 confidence。
- 本版不写 0.8 等固定阈值、不自动给最终好坏标签。待人工样本校准后，按风险确定复核门槛。
- 后续逐条展示结论所依据的句子/能力条目/执行事件。Jev 不生成自然语言推理；可用第二轮从有限 evidence_id 中选择证据或用程序模板展示，不能伪称有模型思维链。
- 明确发现冲突或证据不足时进入复核。临床准确性保持 not_evaluated。
- 生成式模型可对未知意图提出需求描述，再经去重与人工审查形成机会卡；不能把 Jev 的 other 直接当作新需求。

## 6. 100 条样本的构造与使用

本轮优先做全合成 pilot，避免把公开 QA 当成真实产品流量，也便于先审阅自然表达。每条 query 是独立撰写的场景，不是同一句话批量替换病名。100 条分十个采样组，每组十条：症状、报告医嘱、用药、就医、提醒、家庭、长期记录、沟通情绪、边界、产品操作。

这些采样组不是 Jev 金标准，也不是实际需求占比。样本包含清楚表达、短句、错位理解、指代、纠正、重复追问、多人、多诉求、自然结束、可读合成附件及缺失附件。历史回复只负责建立上下文；部分历史回复故意不佳，以测试当前纠正和抱怨。**不能把历史缺陷自动算在未来当前 Answer 头上。**

当前 Answer 全部为 null，执行日志标记 not_collected。留空的意义是把 Query 设计和 Answer mock 分成可审阅的两步，不是将缺少 Answer 判成漏答。

数据文件：../data/query-pilot-100.jsonl。采样审阅信息单独存放于 ../data/query-pilot-100.authoring.jsonl。人类可读版：100条Query审阅.md。尚未有人类受试者或医生验证样本自然度。

下一步先人工抽看首批约 20 条，再生成当前 Answer：正常助手生成与受控对照分别保存；模拟工具状态由 fixture/代码维护。凡对同一个 query 生成变体，都继承 scenario_group_id，不跨开发/测试集泄漏。生成提示、预设错误和人工标签不传给评估器。独立复核“指定的错误是否真的出现在结果中”。
