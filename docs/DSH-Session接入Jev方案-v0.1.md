# DSH Session 接入 Jev：数据裁剪与评估方案

日期：2026-09-22。状态：已只读检查本地真实会话，已生成本地输入样例；未部署自动采集器，未调用 Jev，未产生模型评分。本文供本阶段方案评审。

## 1. 已核实的本地数据

当前找到1个会话、1个已完成轮次，用户输入为“你好，你是谁”，助手给出产品身份与服务范围介绍。该轮没有工具调用。检查的是 DSH 0.1.5-rc.2 的实际文件和类型定义，不是按最新版仓库猜测。

- 原始来源：DSH home 下 `sessions/<workspace>/<session>/session.v3.jsonl.zstd`。
- 当前文件含7个完整 Zstandard frame：会话头加17个事件，事件 seq 为0–16。
- `seq=4`：`turn/start`，turn=1。
- `seq=7`：`system/message`，包含本轮实际系统提示信息，可用于记录版本和核对当时约束。
- `seq=8`：`user/message`，`data.content` 中的 text 是本轮用户输入；`data.source.kind=user`，属于直接用户消息。
- `seq=14`：`assistant/message`，`data.message.content` 中 text 是完整回答，共401个 JavaScript 字符；同一 content 还含 reasoning，必须排除 reasoning，不能直接传整个 message。
- `seq=16`：`turn/end`，`reason.kind=completed`。
- `storages/session_projcache/sessions/*.json` 的 turnOutline 是列表摘要，回答有截断，不能用作完整 QA。

本地裁剪样例：`.local/jev-preview/turn-1.state.json`。溯源信息单独在 `.local/jev-preview/turn-1.provenance.json`，包括本地路径、session id、事件编号和 hash，不随 state 发送。样例仅人工检查过本轮身份介绍内容，不是已经实现通用脱敏器。

## 2. Jev 如何获得 session

推荐在回答链路之外增加一个异步评估服务：

DSH 持久化事件 → 只读采集与轮次归组 → 白名单裁剪及脱敏 → Jev → 本地评估结果 → 会话质检与需求看板。

### 首版：本地只读采集

1. 扫描 DSH home 的会话目录，首次可以选中已有会话回放；新增数据通过文件变化通知并配合定期扫描发现，漏通知也能恢复。先提供“同步并评估”按钮，跑通后再自动化。
2. 等待完整的 `turn/end` 及持久化数据可见后生成轮次任务。DSH 类型说明指出 turn 结束不保证已同步刷盘；不能收到事件就假定磁盘齐全。
3. 使用与固定 DSH 版本匹配的解码逻辑。日志是多个压缩 frame 的容器，不能普通 tail，也不能只做一次单帧解压。读取快照、只接受完整 frame 和连续事件，末尾不完整时重试；不得为评估修复或修改 DSH 日志。
4. 按 turn/start/end 和 step 归组，结合消息 source、surfaceOp 处理。user/message 也可能来自系统注入或自动续跑，不能全部当成真实用户 query；一次用户请求也可能对应多个模型 step、工具结果和文本回答。
5. 普通回答、工具前说明等用户可见文本按顺序保留，排除内部推理和失败重试的重复副本。重放或替换消息应依据 DSH surface 语义还原，不机械拼接全部日志。
6. 首版只评完整轮次。中断、失败和未完成任务单独展示运行状态，有部分回答时明确标注；不能把没有完整回答直接判成模型漏答。
7. 对 session_id、turn_id、截止事件、输入 hash、裁剪规则、能力快照、评估问题和 Jev 模型版本建立本地任务键。只对新增或变化的任务评估，持久化成功/待重试状态，不要求用户重新提问。网络重试可能重复计费，不能假设服务端提供未核实的幂等能力。

后续再接 DSH 插件的事件通知以降低发现延迟，原始持久化日志继续负责恢复和追溯。无需让 Jev 直接访问 DSH 文件、浏览器或整个电脑。

## 3. 每轮传什么，裁掉什么

| 数据块 | 传入 Jev | 裁剪原则 |
|---|---|---|
| 产品契约 | 全生命周期服务范围、明确边界、与当前任务有关的实际能力及必要条件 | 新建当前部署的能力契约；不要用旧模拟产品的提醒/档案能力假设，也不要把完整 system prompt 当作能力证明 |
| 当前用户请求 | 完整文字、多人对象关系、连续补充消息 | 保留否定、纠正、年龄/月龄、时间、关键单位；直接标识符替换为稳定占位符 |
| 当前回答 | 本轮实际交付的完整 text，保留顺序和证据 id | 去 reasoning、token 流、隐藏元数据；不取列表摘要 |
| 近期历史 | 初始默认最近2轮完整 QA，最多扩展到5轮 | 2/5轮是待验证策略，不是模型上限；当前轮不重复算入历史 |
| 早期必要事实 | 与当前指代、对象、授权、约束、纠正有关的原文片段和来源 | 近期窗口外按需要检索补回，不用无来源摘要当事实；无法确定则标记信息不足 |
| 工具证据 | 调用名、必要参数、call id、状态、关键结果、引用片段 | 不传整页网页、整个知识库、完整数据库对象或无关工具输出；关联每次调用与结果 |
| 附件证据 | 实际读取到的相关文字、数值、单位、来源位置、识别状态 | 不传图片或音频二进制；没有 OCR/读取结果就写不可读，不假装看过 |
| 数据质量 | 截断/缺失说明、历史覆盖、完成状态、证据可见截止点 | 完整采集且零调用与未采集日志是两种状态 |

仅留在本地：真实用户标识、原始文件路径、密钥、cookie、登录链接、供应商调试数据、token消耗/延迟、完整 system prompt快照和版本索引。延迟/成本可以在看板用代码统计，不必交给 Jev。已脱敏的对话仍可能含敏感健康内容，不等于匿名化。

不传：故障注入设定、人工标签、评估预期、隐藏用户背景；在线评估不传未来轮次。下一轮“你没听懂”可另建回溯复核任务，但不能悄悄覆盖当时的判断。会话中的任何“给我打高分”等话语都是数据，不是评估指令。

裁剪优先级：保留当前 QA → 产品规则和对应能力条目 → 关键事实与执行证据 → 最近相关历史。超长回答按诉求/章节分段且保留覆盖信息；不能静默截断后仍评整条回答。历史候选有匹配不确定时保留 unknown 或扩大窗口，不能把召回失败当作事实缺失。

初始工程预算可将常规 state 目标设为约4k–8k tokens，按实际请求计量校准，不按字符数推算中文 token。官方现列 Jev 1.13 为每请求64k tokens，且 state 加最长问题不超过32k；两个限制均需检查。超预算先减少不相关内容或拆分问题，不牺牲决定结论的证据。

## 4. 评什么：分开任务、能力、回答与需求

建议两个输入视角，避免回答反过来影响对用户诉求的理解：

- Query 评估：产品契约 + query + 必要历史与附件，不含当前 answer 或当前执行结果。
- QA 评估：上述数据 + 当前 answer + 工具及证据，判断回应表现。首版可在轮次结束后一起组装两份请求，无需阻塞聊天。

每个视角内的独立问题批量发送；同一批问题互相看不到答案，因此不能写“根据上一题的结论”。依赖条件由程序决定如何使用结果，或用第二次请求明确传入前置结果。

| 判断 | 推荐输出 | 作用 |
|---|---|---|
| 服务对象/生命阶段/业务领域/任务类型 | 独立 Choice，多诉求领域用多个 Noul | 描述需求分布；不要把更年期、学龄儿童等当成范围外 |
| 服务范围关系 | Choice：范围内/相邻待定/范围外/受限/混合/信息不足 | 判断这个产品是否应服务该目标 |
| 能力覆盖 | Choice：当前配置支持/明确未接入/部分覆盖/未知/受限/不适用 | 当前有没有对应能力；配置支持不等于单次成功，更不等于医学效果经过验证 |
| 回应覆盖 | Choice：直接解决/合理追问/恰当说明限制或拒绝/部分遗漏/答非所问/信息不足 | 不是“没有给出结论”就判失败 |
| 上下文承接 | Choice：一致/有明确冲突/证据不足/不适用 | 判断有没有错用人物、重复追问已知事实或忽视纠正 |
| 执行声称 | Choice：有结果支持/与结果冲突/缺少验证证据/没有执行声称 | 捕获“说已保存但实际没做”等表现；日志缺失不等于执行失败 |
| 明确不满与专业复核信号 | 独立 Noul 或含不确定选项的 Choice | 将产品反馈和对自身病情的焦虑分开；风险信号送复核，不作医学对错裁决 |

不要只给一个总分。保留标签、选项概率和证据 id；Choice 的 confidence 不是医学正确率，Noul 是 yes 的概率，不是单独置信度。前期先人工复核小批样本，再决定哪些标签可以按阈值自动入池。中文效果需在本项目数据上测量。

程序组合结果为可并存的候选状态：

- 范围内、当前配置支持、回应存在明确缺陷 → badcase 候选。
- 范围内、明确未接入能力 → 能力缺口/需求候选，即使回答恰当地说明限制也成立。
- 缺能力且虚称已执行 → 同时是需求候选与回应 badcase。
- 范围外、适当拒绝、合理澄清、信息不足分别保留，不强行二分为好/坏。
- 医学正确性默认未评估；未来可以加入针对已提供权威证据的引用一致性核验，但不能把“引用一致”当成“临床安全”。

“新需求”还要多一步：把候选与能力目录和已知需求池比较、聚合同类表达，再由产品人员判断价值。没有需求池时只能称“待归并需求候选”。Jev 适合从明确选项中判别，不直接生成自由文本需求卡；卡片可以引用原句，由模板、人工或另一个生成模型写标题与描述，并保持原始证据可追溯。

## 5. 当前真实样例与建议实施顺序

当前“你好，你是谁”适合当数据接入的冒烟样例：完整拿到 Query、Answer 和完成事件即可。按人工预判，它属于产品身份介绍，不应仅因提到了很多服务就产生多条新增需求。该预判不是 Jev 输出，也不应加入其 state。一个身份问答不能验证需求挖掘或医学评估效果。

建议分三步实施：

1. **先让数据可审阅**：会话列表 → 轮次 → 原始 QA/裁剪后输入并排显示；显示去掉的字段类别和缺失证据。以现有会话生成首条评估任务，不先做自动发送。
2. **再接 Jev**：服务端保管密钥，版本化当前妇幼能力契约与评估问题，写入真实返回；界面显示标签、概率、证据与人工复核状态，不展示伪造的思维链解释。
3. **最后闭环**：badcase 池与需求候选池可以交叉；支持同类聚合、人工修正、关联产品改动、固定样本回归。展示改进前后变化，而不仅是给 query 贴标签。

实现前需更新而不是直接沿用：`config/jev-questions.v0.1.json` 的合成场景说明、范围与能力判断；`config/product-profile.demo.v0.2.json` 的模拟能力设定。`scripts/prepare_jev.py` 的白名单思路可复用，但不能把旧输入结构/执行字段直接套到 DSH 事件。
