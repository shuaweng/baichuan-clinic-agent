# 能力边界输入 v0.2：给 Jev 可区分的判据

这版回应 2026-09-21 的对齐反馈：只列“支持提醒、支持家庭健康管理”过于粗糙，不能可靠区分任务的不同操作和条件。此次修改细化模拟产品的输入与题目，未验证 Jev 分类效果。

## 先看文件

- [详细能力配置](../config/product-profile.demo.v0.2.json)：17 项能力，每项都有定义、包含项、不包含项、必要信息、限制、完成证据和邻近反例。
- [Jev 完整请求](../data/examples/alignment-detailed-qa.request.json)：真实请求结构，包含详细产品配置、前文、当前 QA 及 22 个判定问题；没有发送到 API。
- [原公开研究配置](../config/product-profile.v0.1.json)：继续保留真实产品的证据不确定性。新模拟配置不覆盖它。

**下面所有支持、不支持、渠道限制、周期规则均是演示设定，不代表百小医真实能力。** 真实产品落地时应逐条用版本、渠道、文档或实测证据替换状态，不能把演示设定改个标题当成实际产品规格。

## 每张能力卡写什么

| 内容 | 为什么影响判断 |
|---|---|
| 用户要达成的效果 | 判断目标，避免只凭关键词 |
| 动作与对象 | 创建提醒、取消提醒、取消医院预约是不同操作 |
| 支持的触发条件 | 固定时间、周期、用户未确认、记录变化不能混同 |
| 支持的渠道与规则 | App 推送不自动意味着支持电话；每天重复不自动支持任意周期 |
| 完成所需信息 | 时间、对象缺失可以澄清，不等于产品做不了 |
| 不包含的相邻能力 | 帮助定位到别的能力卡；不是全产品“不支持”的声明 |
| 明确不支持的变体 | 只有这里及 unsupported 状态能够证明模拟能力缺口 |
| 完成证据 | 区分生成文字、已创建、已发出、已确认、实际完成健康事项 |
| 正例和邻近反例 | 用一处条件变化解释分类差异；不写当前样本的预设答案 |
| 支持状态与依据 | 本版是 demo_assumption；真实状态未知时不能强行判缺口 |

## 能力目录

| ID | 具体能力 | 模拟状态 | 最重要的区分 |
|---|---|---|---|
| H01 | 症状信息整理与术语解释 | 支持 | 信息整理不等于诊断保证 |
| H02 | 可读报告文字与医嘱解读 | 支持 | 可读文字不等于已经看到图片或全部页 |
| H03 | 图片或扫描文件读取 | 未知 | 读取能力与内容解释分别判断 |
| H04 | 既有用药说明整理 | 支持 | 按医嘱排表不等于决定改药改量 |
| V01 | 用户发起的就医资料清单 | 支持 | 当前生成不等于未来自动整理 |
| V02 | 医院预约交易 | 未知 | 取消预约不等于取消提醒 |
| R01 | 一次性定时提醒 | 支持，有条件 | 确定时间、授权接收人、App 推送 |
| R02 | 固定周期提醒 | 支持，有条件 | 每天/每周，不包括任意条件触发 |
| R03 | 修改或取消已有提醒 | 支持，有条件 | 定位已有任务，保留未要求修改的字段 |
| R04 | 查询提醒任务状态 | 支持 | 任务状态不能证明人已阅读或服药 |
| R05 | 提醒确认回执 | 不支持 | 用户确认与系统发送是两回事 |
| R06 | 未确认超时后通知照护者 | 不支持 | 条件、延迟、接收人变化缺一不可 |
| R07 | 健康记录等事件触发提醒 | 不支持 | 没记才叫与每天定时叫不同 |
| F01 | 保存健康记录 | 支持，有条件 | 持久保存不等于在回复中复述 |
| F02 | 检索已有健康记录 | 支持，有条件 | 已保存可访问记录，不是全知记忆 |
| F03 | 跨账号分享健康资料 | 未知 | 生成给家人看的文字不等于实际发送 |
| A01 | 复诊前自动整理资料 | 不支持 | 定时自动执行不等于被动问答 |

目录并不穷尽所有产品能力。未收录的删除档案、复杂数据导出等请求保留未知，不挤进最近的一类。

## 典型输入与预期区分

前文：用户“想给我妈做复诊提醒。”助手“你希望提醒她本人，还是也通知你？”

本轮 Query：“先提醒她，她半小时没点确认再通知我，能做到吗？”

本轮 Answer：“可以给你妈妈设置固定时间的复诊提醒。你希望几点提醒？”

详细请求沿用这个例子。人工设计预期（不是 Jev 实测结果）是：

- 这是能力可行性咨询，尚不是参数齐备的执行指令。
- 用户目标同时涉及 R01 首次提醒、R05 确认状态，以及 R06 未确认后的延迟升级通知。
- 本模拟配置能做 R01，不能做 R05/R06，因此存在明确能力缺口。
- 回答当前“能做到吗”已有足够能力信息，不能因为未提供具体提醒日期、通知授权等而回避作答。真正执行时仍需补这些信息。
- 当前 Answer 只介绍固定提醒，没有回应条件通知是否支持，因此有核心遗漏。
- 若 Answer 改为“目前只能固定时间提醒，不能在半小时未确认后自动通知你”，回应可合格，能力缺口仍存在。

## 相邻样例：后续实测需要检验的区分

下表均是作者设计的待验证判据，不是人工金标准或模型输出，也没有放进当前请求的待评对话。已有能力卡中的一般例子属于规则说明；若后续测泛化效果，应留出未出现在规则里的表达与组合。

| Query | 应区分的能力或问题 |
|---|---|
| 明早八点提醒我复诊 | R01；执行还需明确日期、时区等上下文 |
| 每天八点提醒我记录一下 | R02 |
| 每天九点看看，没记录才提醒，记过别叫 | R07；不能仅因“每天九点”判为固定周期提醒 |
| 八点叫我妈，八点半也叫我，不管她看没看 | 两项 R01；不是 R06 |
| 她没点确认，半小时后再告诉我 | R05/R06；若创建完整流程还需要首次提醒 |
| 看下妈妈点确认了没 | R05；不同于 R04 查看任务是否存在 |
| 提醒已经建好了吗 | R04；不能推导妈妈已收到 |
| 把那条提醒改到九点 | R03；对象无法定位时澄清 |
| 把医院预约取消，不是提醒 | V02；不属于 R03 |
| 每周五提醒我 | R02 能力支持；本次缺具体时刻 |
| 每月15号提醒我 | 本模拟 R02 明确不支持的周期，不是假定真实产品不支持 |
| 明早给我打电话提醒 | 本模拟 R01 明确不支持的渠道 |
| 现在把明天复诊要带的整理一下 | V01 |
| 以后每次复诊前自动整理 | A01 |
| 写得让我妈看得懂，我自己念给她 | 文本表达要求；不是 F03 实际分享 |

## 判定问题也同步调整

不能只把背景加长而继续问一个“是不是新需求”。完整示例包含：

1. 五个独立 Choice：服务范围、提醒操作类型、能力覆盖、当前任务信息是否充分、当前回答质量。
2. 每项能力一个 Noul，共 17 个：当前目标是否需要该能力。允许多项同时成立，不让复合诉求被强制单选。

需求匹配不看支持状态：一个产品没有的能力，用户依然可能正在要求。各问题只看共同输入，不引用同批其他问题的答案。条件语义仍由完整 Query 和能力规则保留，不能把“有提醒、有通知”两个标签相加就认为满足条件流程。

这 22 个问题是便于审阅的起点，不是已验证的最优数量。尚未用官方 tokenizer 核算请求预算，也未调用 Jev 测试延迟、成本、中文识别率。后续可在保持相邻反例覆盖的前提下精简问题；不能通过只给一个候选类别制造高置信度。
